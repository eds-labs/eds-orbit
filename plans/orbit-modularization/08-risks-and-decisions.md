## 1. Architecture decisions (proposed)

| ID | Decision | Rationale (with evidence) | Alternatives rejected |
|---|---|---|---|
| AD-01 | Modular monolith with a **static module registry**, without dynamic plugins or microservices. | Single team, single Coolify stack (`docker-compose.yml`). Today's extension points are already static maps (`registry.ts`, `action-requests.ts:145`, `specialists/index.ts`). RLS, budget and audit wrap every module the same way. | **Dynamic plugins:** loader, ABI and trust model with no external authors. **Microservices:** split RLS and transactions, and add more operations work. |
| AD-02 | Name the kernel **Orbit Platform** and the main agent **Orbit Assistant**. "Orbit Core" keeps its historical meaning. | "Orbit Core" already names the operator, content packages and agents in docs, flags and status (`docs/plans/ORBIT_CORE_*`, `IMPLEMENTATION_STATUS.md:34`). | **Reuse "Orbit Core":** ambiguous in every future discussion and document. |
| AD-03 | Keep the `Entity` envelope and every kind name. Module ownership is a code registry, with **no data migration** for marketing or knowledge. | About 48 kinds, approval and assignment hashes, `EntityVersion` history and FORCE RLS all depend on the current storage (`shared.ts:73-141`). | **Per-module tables for existing kinds:** high migration risk and hash and approval invalidation, for no functional gain. **Renaming kinds with a prefix:** the same risks. |
| AD-04 | New modules with relational query needs (Support, Projects) get **dedicated tables** in the shared migration chain, with composite tenant FKs, FORCE RLS and grants. | No JSON indexes on `Entity.data`. `list()` loads whole kinds. About 86 JSON-path filters already exist (`01` §5.2). Ticket and SLA queries need indexes. | **Entity for everything:** linear scans. **Separate schemas or DBs per module:** break composite FKs and the single RLS model. |
| AD-05 | Code layout `apps/api/src/platform` plus `apps/api/src/modules/<id>`. The worker imports only the registry. `packages/knowledge` stays the engine. | Minimal moves; the worker and API already share root dependencies via `tsx` (`infra/Dockerfile:34`). | **Package per module:** stronger isolation, but a large move, and Dockerfile and package.json work. Possible later without contract changes. |
| AD-06 | `Workspace` is presented as **Organization** (no table rename). Module activation is **per project** (new `ProjectModule` table). Organization entitlements are deferred. | The tenancy model already exists (`schema.prisma` Workspace, Project). The assignment wants project-level modules. | **New Organization table:** duplicates Workspace. **Workspace-only activation:** too coarse. |
| AD-07 | Permission catalogue: keys declared by modules, mapped to the existing three roles. No custom roles yet. | Checks are scattered over three layers (`01` §6). The first step must reproduce behaviour exactly. | **Full RBAC with custom roles now:** larger auth change before it is needed (Q-10). |
| AD-08 | **Knowledge services in the platform** (retrieval, evidence, facts API, `knowledge_search`, embedding, reindex and eval jobs). The **knowledge module** handles management only. Marketing has a hard dependency on the knowledge module; Support has only an optional one. | The assistant, marketing and future Support all need RAG. The assignment forbids duplicate RAG and requires Support to work without the knowledge UI. | **Everything in the knowledge module:** Support would depend on a UI module. **Everything in the platform:** an overloaded core. |
| AD-09 | Cross-module consistency uses two mechanisms: **in-transaction impact handlers** for safety invariants (knowledge invalidation) and **durable outbox events** for follow-ups. No new broker. | `invalidate()` is atomic today (`packages/knowledge/src/index.ts:101-279`). The outbox and lease system already exists (`worker/main.ts:407-509`). | **Async-only events:** opens a window where revoked evidence is still publishable. **Kafka or NATS:** operations cost. |
| AD-10 | Split the **AI spend mandate** from the **marketing publishing policy**. Step 1 is a projection with no data change; step 2 (separate storage) is optional. | `budget.reserve` consumes the marketing `PolicyInput` (`budget.ts:20`). The `policy` schema mixes both (`packages/schemas/src/index.ts:134-154`). | **Immediate storage split:** changes hashes and conflicts with active assignments. |
| AD-11 | **One assistant** (ADR 0005 §6) with module-contributed tools, prompt fragments and cards. Writes go only through `ActionRequest` executors. **Tool search is mandatory** above about 15 tools. | `MAX_INPUT_BYTES` already had to double (PR #87). ADR 0007 and 0008 already define the model. | **Agent per module:** more model calls and context copies, no safety gain (ADR 0005 alternatives). |
| AD-12 | The web keeps the client-routed catch-all with a **route registry**. URL scheme `/p/:projectId/<module>/…`. Legacy paths redirect. | Next.js never reads the DB (ADR 0001). All views are client components fed by the API (`apps/web/src/components/*`). | **App Router segments per module:** code splitting, but large churn for little gain now. |
| AD-13 | Enforce boundaries with an **extension of `scripts/source-check.mjs`**: baseline first, then ratchet to zero. | No boundary enforcement exists today. No new dependency is needed. | **dependency-cruiser or eslint-boundaries:** new dev dependency, no material benefit at this size. |
| AD-14 | **Existing API URLs, payloads and error codes stay stable.** New module routes go under `/api/projects/:id/<module>/…`. | Web, Telegram, Slack and stored links depend on the current routes. | **Versioned `/v2` API:** duplicated surface. |
| AD-15 | **Support is an own, integrated ticket and communication system** (the `support` module). **Chatwoot is not a dependency.** Channels are adapters behind a provider-neutral domain; a Chatwoot import is optional (E10). | Mario's addendum, 2026-10-13. Keeps provider exchangeability and one data model with project RLS. | **Chatwoot as inbox or backend:** a second system of record and a provider lock-in. |
| AD-16 | Support uses **dedicated tables** (`SupportInbox`, `SupportContact`, `SupportTicket`, `SupportMessage`, `SupportAttachment`, `SupportTicketEvent`, `SupportWidgetSession`) and **platform files** for binaries. | Query and full-text needs (AD-04). Today's base64-in-JSON assets are limited to 1–5 MB (`assets.ts:6-15`). | **Entity envelope:** no indexes. **Base64 in the DB:** size and backup bloat. |
| AD-17 | The livechat widget uses an **embed script, a public API with per-inbox public key, CORS allowlist, hashed session tokens and HMAC-verified identity signed by the host app**. Real-time via SSE with Redis pub/sub. | Desk must not depend on Orbit and Orbit gets no Desk keys (master spec). Only `web` is publicly routed. | **Iframe-only widget:** weaker theming. **WebSockets:** extra infrastructure through the Next proxy. **Desk server calling Orbit:** a coupling. |
| AD-18 | **Support AI is human-in-the-loop by default.** Triage and drafts are automatic. Customer-visible AI answers only evidence-bound, per inbox and opt-in. Autonomous replies only after an eval gate (E1), reusing the agent-review-authority and veto patterns. | The same safety stance as marketing publishing (ADR 0008, `agent-review.ts`, `veto.ts`). | **Autonomous from day one:** unbounded customer risk. |
| AD-19 | **MVP versus extensions** as defined in `06` §2: the MVP covers tickets, contacts, inboxes, e-mail, widget, notes, attachments, notifications, fixed automations, AI triage, drafts and handoff, module roles, REST and public API, and statistics. API tokens, MCP server, autonomous AI, SLA business hours, CSAT, product data, extra channels and the Chatwoot import come later. | Fastest path to a usable desk on the reused Orbit foundations. | **Full scope at once:** about 100+ PT before first use. |
| AD-20 | **Central Orbit MCP gateway** as platform infrastructure. It is a pure protocol and authentication adapter over the shared tool registry, permissions, ActionRequests and knowledge services (`09`). It has no business logic and no MCP-only tools. | Mario's addendum, 2026-10-13. The registry was designed MCP-shaped (ADR 0007). One code path for the UI, the Assistant and MCP. | **Separate MCP application with its own logic:** duplicate rules and drift. **Hosted or third-party MCP gateway:** credentials and data outside Orbit's RLS and budget journal. |
| AD-21 | **Orbit is its own OAuth 2.1 authorization server** (Better Auth OAuth provider with the MCP and CIMD packages and the `jwt` plugin, pinned past known advisories). It uses CIMD first, DCR for backward compatibility only, PKCE S256, RFC 9207 `iss`, resource-bound JWT access tokens and rotating refresh tokens. A consent screen selects organization, projects and scopes and stores an `McpGrant`. | It shares users and sessions with Orbit and meets the ChatGPT and MCP 2026-07-28 requirements. | **External IdP (Keycloak, Auth0):** a second identity store and more operations. **Static API keys:** ChatGPT does not support them. |
| AD-22 | **Client-side confirmation is never authorization.** MCP exposes R0, P and selected W0 tools. Every consequential action is an ActionRequest decided in Orbit (inbox, Telegram, or a URL elicitation to an Orbit page). Hard floors are never exposed. MCP-originated requests default one step stricter, with per-grant quotas and a kill switch. | ChatGPT notes that writes can occur despite read-only hints. Always-on dots act without step-by-step supervision. | **Trusting the client's write confirmation:** not under Orbit's control. |
| AD-23 | The MCP gateway runs as its **own compose service `mcp`** from the same image, served under the **path `https://orbit.eds-labs.io/mcp`** (Q-22, decided 2026-10-13). There is no subdomain; Traefik routes `/mcp` and its Protected Resource Metadata paths to the service. It is stateless and supports MCP protocol revisions 2025-11-25 and 2026-07-28. | The Next proxy forwards no `Authorization` header and only `/api/*`, and aborts at 45 s (`route.ts:41-66`). Isolation of load and failures without a DNS change. Stateless design matches the current spec. | **`/mcp` inside the API process:** shared event loop and limits. **Own subdomain:** cleaner, but needs a DNS change. **Through the Next proxy:** a header and timeout mismatch. |

## 5. Assessment summary

| Topic | Assessment |
|---|---|
| Suitability for modularization | **Good foundation, weak boundaries.** The safety infrastructure (RLS, roles, budget ledger, ActionRequests, outbox, telemetry, runtime port) is domain-neutral and reusable. Storage by `kind` allows ownership changes without data migration. Missing pieces: enforced boundaries, open registries, composition roots, and a separation of the AI spend mandate from the marketing policy. |
| Unchanged components | `packages/knowledge` (except `invalidate`), `packages/connectors`, `packages/creative`, `packages/db`, all tables and kinds, RLS policies, Better Auth, budget ledger, telemetry tables, runtime port, ActionRequest mechanics, outbox and lease logic, Compose, Coolify and backup, design tokens. |
| Most problematic dependencies | (1) `policy.ts` as the budget source for all paid operations; (2) `invalidate()` writing marketing state; (3) `enqueue` and the scheduler inside marketing, plus the worker importing API internals; (4) closed registries and the marketing-hard-coded assistant prompt; (5) the monolithic `server.ts` action dispatcher and `orbit.tsx` navigation. |
| Effort: Platform/Marketing | About 57–83 PT, Phases 0–2. |
| Effort: Knowledge split | About 14–21 PT, Phase 3. |
| Effort: Support | Platform prerequisites about 18–27 PT (WP4.2, WP4.3, WP4.5–WP4.7). Support MVP about 42–62 PT (WP5.1–WP5.9). Extensions about 50–80 PT. |
| Support reuse | Outbox, jobs and leases (`outcome_unknown`), scheduler, notify-in-transaction, Telegram transport, agent runtime and runner, tool registry, ActionRequests, agent-review authority and veto patterns, hybrid RAG with rights and evidence, budget and telemetry, credential vault, chat UI components. **New:** public ingress, real-time fan-out, files, e-mail, in-app notifications, module roles, API tokens and MCP (later). |
| Effort: MCP gateway | Track M about 21–33 PT. Can run after Phase 3, in parallel with Phase 4 and before Support. |
| MCP reuse | Tool registry (MCP-shaped by design), permissions and module roles, ActionRequests, knowledge services with rights filters, budget and audit, Better Auth users and sessions. **New:** OAuth authorization server, consent and grants, gateway service, per-token limits. |
| Most critical risks | Modularization: R-01 (production marketing), R-02 (permissions), R-04 (missed invalidation), R-07 (merge conflicts). Support: R-15 (customer PII), R-17 (public attack surface), R-18 (unsafe AI answers). MCP: R-22 (data exfiltration), R-23 (OAuth flaws). Pre-existing F-01 (add-member).
