# Orbit API v1 (machine API)

The versioned API for integrations such as websites and import tools ([ADR 0029](adr/0029-content-module.md), plan [CONTENT_HUB.md](plans/CONTENT_HUB.md), work packages CH1.1 and CH1.2). It is separate from the internal `/api/projects/...` routes of the Orbit web app. The OpenAPI document is `packages/schemas/openapi-v1.json`, generated by `pnpm api:generate`.

Status: implemented on the Content Hub branch and switched off by default (`ORBIT_API_V1=false`). The Content module's delivery, preview and management routes (CH1.12, CH1.13) are described in [CMS_API.md](CMS_API.md).

## Keys

- A project owner creates keys under `POST /api/projects/:projectId/api-keys` (UI in the settings center follows in CH1.14f).
- A key belongs to one project and carries scopes that modules register, e.g. `cms:delivery.read`. Write scopes must be confirmed with `confirmWrite: true`.
- The token `ok_<12>_<43>` is shown once. Orbit stores only its SHA-256.
- Scopes, resource filter (e.g. `siteIds`) and expiry never change after creation; replace a key instead. The default expiry is 365 days; `expiresInDays: null` means no expiry.
- Revoking (`POST .../api-keys/:keyId/revoke`) takes effect on the next request. Creation and revocation are audited without secrets.
- A key never acts as a member: it cannot decide approvals, and write scopes only create drafts or proposals that people in Orbit decide.
- Switching a module off (installation flag or project setting) disables its scopes.

## Requests

- Send `Authorization: Bearer ok_…`. Session cookies are ignored under `/api/v1`, and no `Origin` header is needed.
- Use keys only on servers. A key in a browser bundle is exposed to everyone.
- `GET /api/v1/key` returns the calling key's prefix, project, scopes and filter.

## Answers

| Topic | Rule |
| --- | --- |
| Errors | `{ "error": { "code", "message", "detail" } }` with a stable `code`. Every v1 answer carries `X-Request-Id`. |
| Authentication | Every credential problem is `401 API_KEY_INVALID`. A missing scope is `403 API_KEY_SCOPE_MISSING`. |
| Rate limits | Per minute, by kind of route (delivery 600, management 120, preview 60), counted twice: per client address before the key is checked, and per authenticated key afterwards. A request with a wrong or forged key counts only against its address, never against the key whose prefix it names. `429 RATE_LIMITED` when exceeded. |
| Caching | Cacheable reads send `ETag` and `Cache-Control: private, max-age=60, stale-while-revalidate=86400, stale-if-error=604800`. `If-None-Match` answers `304`. |
| Idempotency | Writes accept `Idempotency-Key` (8–128 characters of `A-Z a-z 0-9 _ . : -`). The same request within 24 hours replays the stored answer with `Idempotency-Replayed: true`. A different request with the same key is `422 IDEMPOTENCY_KEY_REUSED`. A parallel first use is `409 IDEMPOTENCY_KEY_IN_USE`: retry it. Server errors are not stored. |
| Pagination | `?limit=&cursor=` returns `{ "items": [...], "nextCursor": string \| null }`. Cursors are opaque. |

## Versioning

- Additive changes (new fields, endpoints, scopes) keep `/api/v1`. Clients must ignore unknown fields.
- Breaking changes go to `/api/v2`, with at least six months of both versions in parallel and `Deprecation`/`Sunset` headers on the old one.

## Operations

- Enable it with `ORBIT_API_V1=true`. While off, every `/api/v1` route and the key management answer 404.
- Rollback: switch the flag off. The tables `ApiKey` and `ApiIdempotencyKey` stay; keys can be revoked individually.
- Stored idempotent answers are deleted hourly after they expire.
