# Knowledge architecture

Status: locally implemented; verification results are recorded in RAG_EVALUATION_REPORT.md. No live embedding quality or production acceptance is implied.

## Contract and trust boundaries

`packages/knowledge` is a domain package used by API and worker. It never publishes, calls a model, spends money or opens host administration. The API derives `Scope {workspaceId, projectId, userId}` after authenticating and authorizing membership. Every entry point receives a `DbTx` created by `packages/db.scoped`: transaction-local workspace/project settings and a project advisory lock serialize imports, permissions, fact changes, budget allocation and publishing preflight. The lock key is `hashtextextended(workspaceId + ':' + projectId, 0)`.

Prisma 7 uses `@prisma/adapter-pg`. Scalar domain data uses Prisma, PostgreSQL `tsvector` and dimension-checked `vector` use parameterized Prisma SQL. The migration enables pgvector, FTS triggers, GIN indexes, composite foreign keys and FORCE RLS. Business roles must be nonowner, NOSUPERUSER, NOBYPASSRLS. The separate authentication role can access only Better Auth's four core tables and Workspace/WorkspaceMember/Project/ProjectMember; it has no business table grant. Auth is the control plane and must remain confined to the trusted API/worker. A database role is not an end-user identity; RLS adds a second boundary after server authorization.

## Persistence

- `Entity` stores schema-validated sources, facts, evidence and product workflow objects. EntityVersion holds prior snapshots. Scoped composite keys prevent references into another workspace/project.
- `KnowledgeDocument` has a stable `(workspace, project, source, externalId)` identity and an active version pointer constrained to its own document.
- `DocumentVersion` records hash, extraction version, source generation, fetch/source-update times, validity, language and complete text. Versions are prepared and activated in one transaction; a failed batch rolls back completely.
- `KnowledgeChunk` records structured heading, paragraph/page anchor, text, hash, token estimate and DE/EN plus identifier FTS vectors.
- `ChunkEmbedding` records OpenAI model/profile, exact dimensions, generation and pgvector data. The initial approved provider profile is `openai:text-embedding-3-small:1536:chunk-v1`. The immutable registry additionally supports separately built `text-embedding-3-large` profiles at 1536 or 3072 dimensions; registering storage compatibility does not authorize provider expenditure or activation.
- `KnowledgeIndex` holds the immutable profile/generation/corpus manifest and recorded evaluation. Migration 002 preserves baseline vectors, removes the fixed vector typmod, checks `vector_dims(vector)=dimensions` and exact supported model/profile combinations, and constrains vectors to their scoped index generation. A partial unique index permits only one active generation per project. Retrieval materializes the selected profile/dimension/generation relation before evaluating cosine distances, so a different dimension never reaches the distance operator.
- Revocation entities persist source/external identity fences even after text and vectors are physically removed. Outbox events request reconciliation for remotely scheduled/uncertain publications. AuditEvent is append-only under business RLS.

## Import

TXT, Markdown, sanitized HTML, text PDFs and bounded DOCX are supported. HTML parsing makes no subrequests and executes no scripts. PDFs use PDF.js with evaluation disabled in a dedicated child process with an empty application-credential environment, a 96 MB V8 heap budget and a 10-second kill deadline; deployment container limits remain necessary for total native/array-buffer memory; encrypted/invalid/scanned files produce explicit extraction errors. DOCX preflight verifies exact directory counts/boundaries and local-header consistency, rejects duplicate/path-changing entries, encrypted archives, macro payloads, excessive expansion, ZIP64 and DTD/entities, and performs bounded actual decompression before Mammoth extraction. OCR and MDX execution are absent.

Public fetching requires explicit HTTPS origin and path allowlists. It rejects private/non-global IPs, checks all DNS answers and pins the chosen address to the TLS connection, preserves hostname certificate checking, disallows redirects/compression, bounds bytes and wall time, and checks MIME. The API uses `fetchApprovedDocument`, which checks robots.txt before the page, including agent-specific rules and a bounded wildcard matcher; unknown failures deny access and absent robots.txt permits the approved URL. DNS resolution is cancellable and shares the overall request deadline. Bounded sitemap/feed discovery only extracts approved references; it never recursively fetches resources.

Unchanged normalized content and document metadata reuse the active document/chunks/vectors and updates technical sync time. Changes to text, title, language, MIME, canonical URL, source update time or validity produce a new version; dependent verified facts become candidates for review. Existing fact values are never overwritten by a document. A source generation carried by asynchronous jobs prevents revival following a pause, rights change or revocation. `attachEmbeddings` accepts only a complete current version and rechecks model permission/generation after an external provider operation. Provider calls and atomic cost reservations belong to the worker.

## Retrieval and facts

`retrieve` accepts purpose, publication time, language, required source IDs and fact keys, market, query and optional query vector/profile. `forModel:true` is required when its contents will be transmitted to OpenAI. Structured facts are resolved by key/language/market and half-open validity intervals. Decimal values remain strings with explicit currency/unit. Conflicting active values mark both records conflicting; no relevance score selects a winner. Explicit supersession is scoped to the same key/language/market. Owner conflict correction supplies `resolveConflictIds` covering every currently overlapping verified/conflicting peer in that group; incomplete, duplicate or mismatched sets and candidate replacements are rejected. The verified replacement keeps each predecessor identity and snapshots while marking them superseded. Required sources constrain facts and both SQL retrieval branches; an unavailable mandatory source produces an explicit gap.

Lexical candidates use PostgreSQL's DE/EN full-text search plus a simple identifier index and exact substring path. This is PostgreSQL FTS, not BM25. Semantic candidates use exact pgvector cosine search with identical project, source, generation, permission, freshness and validity predicates. Up to 40 candidates per branch are combined using reciprocal rank fusion, then duplicate hashes, per-document dominance and context size are bounded. Initial top-k is 8 (maximum 10), three chunks per document and approximately 6,000 context tokens. Token count is a conservative character heuristic, not a tokenizer claim.

Without a query vector the evidence explicitly reports `lexical_degraded`; this cannot satisfy the live semantic gate. Generated sources are excluded as independent fact evidence. Each evidence item contains the concrete chunk and document-version IDs, source generation, original anchor, selection branches, rights and timestamps. Citation URLs discard queries/fragments and reject embedded credentials; source retrieval never follows citations as instructions.

`withdrawFact` checks the expected fact version, records a revoked version and invalidates referenced evidence, drafts, approvals and publication intents while retaining correction history. Unrelated facts remain usable; factual withdrawal does not imply erasing its authorized audit history.

`validateEvidence` must run immediately before execution in the same protected transaction as publication intent/guard checks. It rechecks evidence status/purpose, current fact versions, source generation/rights/embargo, active document version, chunk existence, freshness and validity. Retrieval relevance scores are never probabilities, truth assessments or execution authority. Empty/conflicting/missing required facts produce explicit gaps and insufficient evidence.

## Controlled index generations

`beginIndexBuild` captures a stable, permitted current-chunk manifest under the project lock. `attachIndexBatch` accepts bounded, dimension-checked immutable batches only for that manifest; retries do not overwrite vectors. Corpus changes, source revocation or rights-generation changes reject the old build. Building generations remain invisible to normal retrieval.

`evaluateIndexGeneration` executes filtered exact SQL against a complete generation and records the dataset/config/corpus, result ranks, attribution of forbidden hits, Recall@10, MRR and settled provider receipts bound to that immutable index ID and evaluation dataset. Build receipts use `projectId:index:indexId:build:jobId` with category `reindex`; evaluation receipts use `projectId:index:indexId:evaluation:datasetVersion:jobId` with category `reindex_evaluation`. Both must have positive settled usage; unrelated project expenditure cannot satisfy the gate. Activation requires at least 60 cases (48 answered, 12 negative), Recall@10 >= 0.90, zero forbidden hits, current complete corpus, and a passed live evaluation. Recorded evaluations bind the model/dimensions/distance, retriever/chunk versions, dataset SHA and source/chunk manifest; a 30-day validity window requires re-evaluation after expiry. `validateActiveIndexEvaluation` checks that record, current corpus and still-settled bound receipts at readiness/publication time. Environment flags cannot substitute for the stored proof. Evaluation input belongs to the trusted provider/evaluation adapter, never a client claim that supplied vectors are live. The runtime provider adapter accepts only the registered combinations: `text-embedding-3-small` at 1536 dimensions and `text-embedding-3-large` at 1536 or 3072 dimensions. Query embeddings follow the active index; reindex/evaluation batches use their bound build profile. The single-document embedding action remains baseline-only and rejects a different active profile before spending. Every paid path still requires the model allowlist, current rate card, approved budget and applicable profile/corpus guards; registry support is not a claim of live model acceptance.

Before the first alternate-profile activation, the initial baseline must itself receive a complete built/evaluated checkpoint; an unevaluated legacy baseline cannot be presented as a valid rollback target. `activateIndexGeneration` atomically retires the old generation and switches the active one. `rollbackIndexGeneration` applies the same completeness, evaluation and current-rights requirements to a retired generation; it cannot revive purged/revoked data. Every evidence pack records the generation ID, and execution preflight refuses evidence from a different active generation. Changes to the corpus require a fresh generation/evaluation before a retired index can be restored.

Synthetic-vector activation exists only for executable integration tests, requires an explicit internal test option, `NODE_ENV=test`, a configured isolated test database, and a paused Observe project. Public API routes do not expose that option. Runtime retrieval rejects an active synthetic evaluation outside test mode. The SQL mechanics have been executed locally at 1536 and 3072 dimensions; live model quality and paid background-build acceptance remain external gates.

## API exports

`ingest`, `retrieve`, `setFact`, `withdrawFact`, `validateEvidence`, `revokeSource`, `revokeDocument`, `setSourceRights`, `attachEmbeddings`, `extractDocument`, `fetchApprovedDocument`, `discoverPublicPages`, and `fetchPublicDocument` are exported from `packages/knowledge/src/index.ts`, alongside `getActiveIndex`, `assertActiveEmbeddingProfile`, `assertIndexCorpusCurrent`, `validateActiveIndexEvaluation`, `listIndexGenerations`, `beginIndexBuild`, `attachIndexBatch`, `evaluateIndexGeneration`, `activateIndexGeneration`, and `rollbackIndexGeneration`. Authentication and role checks belong to API handlers, never to untrusted input metadata. No global RAG cache exists: every retrieval checks database state, so there is no cross-project cached context to invalidate.
