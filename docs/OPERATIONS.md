# Operations

## Start and inspect

Use the actual setup commands in `README.md`; production variants are in `DEPLOYMENT_BOOTSTRAP.md` and `SHARED_HOST_DEPLOYMENT.md`. The local dependency stack is isolated on 127.0.0.1:55432/56379. `pnpm dev` starts API, web and a separate worker; the deployed worker does not depend on a browser, Mac chat session or Codex.

`GET /health` checks database connectivity. The authenticated Operations screen reads durable jobs, undispatched outbox rows, knowledge/provider exceptions and a Redis worker heartbeat (fresh within 30 seconds). The worker also writes an atomic local health file used by its container check. Heartbeats describe the configured publisher instance and queue classes; they do not certify external publishing or model quality.

Queues: publishing concurrency 2; generation, ingestion, embedding, reindex, index evaluation, analytics, reconciliation, Slack notification, image, `agent`, `telegram_notification` and `postiz_draft` concurrency 1 each (the last three belong to Orbit Agents, see below). PostgreSQL holds all business states; Redis holds transport. Pump interval is 1.5 seconds, dispatch batch 40, waiting high-water mark 200 per queue, lease 120 seconds (180 seconds for `agent` and `telegram_notification`) and at most three job attempts. Publishing has a separate queue so index work cannot exhaust its queue slot. A full memory/corpus workload capacity benchmark is not implied by these limits.

The queue pump only processes projects whose `Project.workDueAt` marker is due (indexed, read through the existing `orbit_auth` Project access; it holds a timestamp, no business data). Invoker-rights triggers move the marker earlier: an `Entity` insert/update marks its project due now, an undispatched `Outbox` row marks it due at `availableAt`, and a `Project` change other than the marker (pause, mode, generation) marks it due now. Project RLS still applies to every trigger update. After processing a project inside its scoped, advisory-locked transaction (sweep, lease reclaim, outbox read), the worker sets the marker to the earliest of the next undispatched outbox row, the next running-job lease expiry, the next time-based sweep transition (`nextSweepAt`: mission start/end/follow-up, periodic source sync slot, running experiment end, the 10-minute autopilot plan check), the next saved Matomo import (12 hours after the last run), a pending Drive retry, or at most five minutes later as a safety net. A trigger only moves a marker that lies later than the new work, so a due marker would not record a write that lands while the project is being processed. The worker therefore claims a due project first by moving its marker 60 seconds ahead (processing lease; a project that is no longer due is skipped); any write committed after the claim, including the pass's own, moves the marker back. The final update is conditional on the claimed value, so such a write keeps the project due for the next tick instead of waiting up to five minutes. A crashed pass is retried after the lease. Each tick handles up to 100 due projects oldest-first with four concurrent projects; a full batch schedules the next tick after 50 ms. A failing project is retried after five seconds without blocking others, and the Drive connection check is gated to once per 30 seconds per project whether or not Drive is enabled. Idle projects cost no transaction per tick.

The worker creates the directory of `WORKER_HEALTH_FILE` before writing it. Pump failures are logged as `Orbit queue pump unavailable (<code>)`, where the code is an uppercase domain code, a driver/system code such as `ENOENT` or `P1001`, or the error class name; error messages, paths and URLs are never logged. `WORKER_WORKSPACE_ALLOWLIST` (comma-separated workspace UUIDs) restricts the pump to those workspaces for isolated acceptance runs; it is accepted only with `EXECUTION_MODE=test` and stops the worker at startup otherwise.

Migration `202609300001_project_work_due` is additive and forward-only; existing projects become due at migration time and settle after one pass. Rolling back the worker code alone is safe because the old pump ignores the marker. To remove the schema part as well, stop the worker and run as the migrator: `DROP TRIGGER project_mark_due ON "Project"; DROP TRIGGER entity_mark_due ON "Entity"; DROP TRIGGER outbox_mark_due ON "Outbox"; DROP FUNCTION orbit_project_mark_due(), orbit_entity_mark_due(), orbit_outbox_mark_due(); DROP INDEX "Project_workDueAt_idx"; ALTER TABLE "Project" DROP COLUMN "workDueAt";` and delete the `_prisma_migrations` row for that migration.

Compose caps API/web at one CPU and 768 MiB each, worker at two CPUs/1536 MiB, database at two CPUs/2048 MiB and Redis at 0.5 CPU/384 MiB. Redis reserves 256 MiB with `noeviction` and AOF; application state is recoverable from PostgreSQL/outbox. Containers use bounded logs and process counts, dropped capabilities, no-new-privileges, non-root runtime and a read-only application filesystem. CPU/RAM limits do not guarantee host disk IOPS, free-space isolation or all-neighbor latency. See the hosting report for measured versus proposed capacity.

## Agent telemetry, cost attribution and API logs

Migration `202609300001_agent_telemetry` adds `AgentRun` (one row per chat run, generation, retrieval, ingestion, reindex, index evaluation or image call; kind, agent name, task class, subject, optional mission, status, duration, error code) and `AgentSpan` (model call, tool call, embedding or image span with model, status, attempt, duration, token counts, cost micros, budget reservation ID and provider response ID). Both tables are project-scoped with forced row level security (`project_scope`). `BudgetReservation` gains nullable `agentRunId`, `taskClass`, `model` and `missionId`. The migration is additive; deploy it with the normal migration step before the API that uses it.

Telemetry stores only bounded codes, hashes of inputs/outputs, counts, durations, model names and IDs. Prompts, tool arguments, model output, source text and provider error messages are never written. Recording is non-throwing: a failed telemetry write is logged by error class only and never changes a chat, generation or ingestion result. A chat run whose outcome is unknown after a crash is closed as `blocked` with `CHAT_OUTCOME_UNKNOWN`. An image span that succeeded carries no cost (`costMicros` null); the reservation stays unknown and counted, as before.

Editors and owners read this through `GET /api/projects/:projectId/agent-runs` (newest first, 50 per page, optional `kind`) and `GET /api/projects/:projectId/ai-cost`. For cost per model or per mission use `?groupBy=model` or `?groupBy=mission` (other groupings: `day`, `category`, `taskClass`); the default range is the current UTC month and at most 93 days. Each row reports `reservedMicros` (reserved or in flight), `settledMicros`, `unknownMicros` and `count`; released reservations are excluded, rows without attribution (older reservations) appear under key `null`. Unknown amounts are real exposure and are not free. Cost micros are USD micros of the configured account currency.

The API uses the Fastify pino logger. Each request logs a random request ID (client IDs are ignored), method and path without the query string; each response logs the status code. Authorization and cookie headers are redacted and request or response bodies are never logged. A failed request adds one line `{code, status}` (level `warn` below 500, `error` from 500) and, only for errors outside the known domain/validation classes, `errorName`; never the message or stack. `/health` and `/api/health/ready` log at `warn` so probes do not flood info logs. Set `LOG_LEVEL` (`trace|debug|info|warn|error|fatal|silent`, default `info`); the test suite defaults to `silent`. Worker logging is unchanged by this phase.

Rollout note (cache-aware estimates): the higher estimate raises the first-draft cost ceiling stored with Chat proposals. Before deploying this phase, confirm or discard every pending Chat proposal. A proposal still pending afterwards fails confirmation with `PROPOSAL_COST_CHANGED`, and a mission confirmed before the deploy but generated after it may stop earlier with `CHAT_PROPOSAL_COST_EXCEEDED`. Both checks fail closed before any paid call, so nothing is overspent; recovery is to ask Chat to propose the campaign again. See ADR 0003.

## AI providers and the Claude budget

Settings → AI (owners) shows both providers, the verified models with their prices and task classes, the Claude credit budget and the usage. The Anthropic key is saved encrypted through "Configure Claude" (`ai-provider-configure`); `ANTHROPIC_API_KEY` in the environment is a bootstrap fallback only. Read the spend per provider with `GET /api/projects/:projectId/ai-cost?groupBy=provider` and the Claude budget with `GET /api/projects/:projectId/ai-budget`: `level` goes `ok` → `warn` (first threshold) → `warn2` (second) → `stopped` (the internal stop, from which `reserve` refuses Anthropic models with `PROVIDER_BUDGET_STOP`). The attention item `platform_provider_budget` (warning, critical when stopped) points owners to the settings. The spend is Orbit's own calculation; the remaining credit in the Anthropic console is entered by hand ("Credit balance (manual)") and shown with its verification time, never as a live value. When the credit renews, keep `anchorDay` at the renewal day; to continue after a stop raise the stop or wait for the next period. A stop with the fallback setting `openai` routes new calls to the task's OpenAI tier at OpenAI prices; the spans say `(fallback)`. Spans of Claude calls are named `messages.create` / `messages.stream` in Operations → AI runs. Live check without the application: `ANTHROPIC_API_KEY=… node scripts/anthropic-smoke.ts` (one Haiku call, at most 64 output tokens, prints the usage and the cost at the catalog prices).

## Model routes and generation evals

Routes per task class (`chat_operator`, `draft_social`, `draft_blog`) are set by the owner in the OpenAI configuration dialog; precedence, effort and ceilings are described in `MODEL_ROUTING.md`. Migration `202610010001_agent_run_route_version` adds the nullable `AgentRun.routeVersion` (the configuration's entity version); it is additive and deploys with the normal migration step. With no task route saved, behaviour is unchanged.

Rollout note (route-priced blog proposals): Chat proposals for blog content are now priced with the `draft_blog` route (quality tier) instead of the standard tier. Before deploying, confirm or discard pending blog proposals; one still pending afterwards fails confirmation with `PROPOSAL_COST_CHANGED` when the two tiers differ in price, before any paid call. Ask Chat to propose it again.

Saving the OpenAI configuration (any field, including image-only settings) while a chat run or draft generation is in progress stops that run before its next paid call with `CHAT_ROUTE_CHANGED` or `GENERATION_DEPENDENCY_CHANGED`. Save routes when no run is active, or retry the stopped run. A route model that is no longer in the verified allowlist fails closed with `MODEL_CAPABILITY_NOT_VERIFIED`.

Before switching a route, run the generation eval (`evals/generation/README.md`): the dry run (`pnpm eval:generation` with the local environment) prints the plan, the worst-case cost, the ceiling (at most $5) and the confirmation value; the live run needs Mario's key in `ORBIT_EVAL_OPENAI_API_KEY` and the printed confirmation. It runs only against the local database and writes metrics-only evidence to `docs/evidence/generation-eval-<UTC>.{json,md}`. Roll back a switch by saving the previous route or clearing the task route.

## Postiz queue watch

Postiz can accept posts while its orchestrator (the Temporal worker that sends them) is hung: on 2026-10-01 the orchestrator hung at startup after a container restart, wrote no log line and left every scheduled post in `QUEUE`. A `pm2 restart orchestrator` inside the Postiz container released it. Orbit now detects this state.

For each project with a verified Postiz connector and assigned channels, the worker reads the Postiz posts of the last seven days at most every 10 minutes (read-only `GET /posts`; the public API allows only a few calls per hour). A post of an assigned channel that is still `QUEUE` more than 15 minutes after its publish date opens the exception `POSTIZ_QUEUE_STALLED`; a failed read opens `POSTIZ_QUEUE_CHECK_FAILED`. Both carry a title and an instruction, appear under Approvals and in the Overview count, and close themselves after the next good check. The last result is stored per project in `postiz_queue_watch`.

The worker also writes each project's result to the Redis hash `orbit:postiz-queue:<PUBLISHER_INSTANCE_ID>`. The public `GET /api/health/postiz` returns `{"status":"ok"}`, `{"status":"unknown"}` (no check within the last 30 minutes, for example no assigned channel) with HTTP 200, or `{"status":"stalled"}` with HTTP 503. Point an external monitor (Uptime Kuma) at it with an interval of 5 minutes. When it alerts: in Coolify open the Postiz terminal, run `pm2 logs orchestrator --lines 30 --nostream`, and if it shows no "Nest application successfully started" run `pm2 restart orchestrator`. Overdue posts are sent immediately afterwards; delete queued test posts in Postiz first. After every Postiz restart or redeploy, check the orchestrator log once.

## Content packages (Orbit Core)

`ORBIT_CONTENT_PACKAGES=true` lets Orbit Chat offer `request_content_package` and `package_status` (default `false`). A package is one draft-only mission per channel; it starts only after the requesting user clicks "Start package" on its card, which decides its `content_package.start` action request. Drafts are prepared immediately through the normal generation path and share the run key `package:<id>`; nothing is reviewed for publishing, scheduled or published. Turning the flag off stops new packages and new starts; already started packages finish as ordinary draft-only missions. No migration is involved, so a rollback is a revert. An owner's package may include one image; it runs in the `image` worker queue with one attempt and counts toward the package's run key. A package image with `outcome_unknown` was sent without a stored result: check the provider usage, never resend it automatically. Cancel pending packages before rolling back code that removes the `image` queue. A package revision is an ordinary draft-only mission with `revisionOf`; it never regenerates the image. With the flag on, `propose_schedule` lets editors and owners propose one package draft for a slot; only an owner's approval of that `content.schedule` request in the approvals inbox schedules the exact post. Approval lets that package mission publish this one post (audit `mission.publish_authorized`, test or live by `EXECUTION_MODE`) and creates an ordinary publication. "Cancel schedule" on the package card (`POST …/chat/packages/:id/unschedule`, the requester or an owner, also with the flag off) withdraws open proposals and takes a publication back before the handoff together with its publishing job and the mission's publish right (audits `publication.withdrawn`, `mission.publish_revoked`). A post being handed over (`sending`) or already handed over (`published`, `published_test`, `outcome_unknown`) is reported and never retracted or sent again; a Postiz post must be removed in Postiz itself. Moving a post is a new `content.schedule` proposal that the owner decides; the post keeps its slot until then. Reconciliation of handed-over posts uses the existing `reconcile` action. With `EXECUTION_MODE=live` and external writes on, an approved schedule is a real public post. Turning the flag off stops new proposals and decisions; already approved schedules stay ordinary publications and can still be canceled from the card before the handoff. A package image reaches a post only after an owner confirmed its usage rights (`asset-status`) and the requester attached it (`content_package.image_attached` audit); revoking the rights later blocks the post in preflight (`ASSET_NOT_APPROVED_OR_UNSUPPORTED`).

Both feature flags are set as Coolify environment variables; `docker-compose.yml` passes them to the API and the worker, and a redeploy applies a change. `ORBIT_TOOL_SEARCH=true` (default `false`) makes Orbit Chat load six rarely needed tools (`approved_assets`, `analytics_memory`, `revise_package_deliverable`, `recent_content`, `schedule_options`, `propose_schedule`) only through client-executed tool search, and only when the chat route's model is `gpt-5.4` or later; otherwise every tool loads as before. The search runs in Orbit without a model call and returns only tools the user's role may use (span `tool_search`). Before enabling it in production, run one approved small chat that needs a deferred tool on the configured model; if the provider rejects `tool_search`, turn the flag off (no migration, effective for the next run).

## Orbit Agents

`ORBIT_AGENTS=true` (default `false`) turns on assignments, their background specialists, the veto window and the private Telegram bot ([design](superpowers/specs/2026-10-09-orbit-agents-design.md), ADR 0005 and 0008 addenda). `ORBIT_IMAGE_REFERENCES` (default `false`) sends approved style references as reference images; while it is off the visual step uses a written style description of them. `ORBIT_AGENT_REVIEW_AUTHORITY` (default `false`) is the gate of the review agent's authority (spec §6, ADR 0008 addendum): only while it is `true` can an accepted agent review stand in for the owner's review and let an assignment post go out after its veto window. Set it to `true` only after the live review eval has passed (rollout Approval J); while it is `false` the bot still sends previews and Stop works, and assignment posts wait for the owner. `docker-compose.yml` passes all three to API and worker, checked by `pnpm test:coolify-compose`. The rollout, approvals H–K and the rollback are in the [rollout plan](plans/ORBIT_CORE_ROLLOUT_PLAN.md), Phase 7. Migration `202610090001_agent_run_kind` is additive (it widens the `AgentRun.kind` check by `agent`) and runs with the normal migration step.

`ORBIT_MODULES` (default `false`) lets owners switch modules per project (`PUT /api/projects/:id/modules/:moduleId`, WP1.4 of the modularization plan in plans/orbit-modularization, ADR 0009). The choice is recorded in `ProjectModule` and audited. With the flag on it is enforced (WP2.4, `docs/MODULE_ACTIVATION.md`): a disabled module's routes, actions and collections answer `404 MODULE_DISABLED`, the assistant leaves its tools out, the sweep skips it and the worker stops its jobs as `blocked_dependency` / `MODULE_DISABLED`. Nothing is deleted. Setting the flag to `false` makes every module enabled again at once; blocked jobs are then restarted with `retry`. Migration `202610130001_platform_project_module` is additive: it creates `ProjectModule` (FORCE RLS, `orbit_app` may select, insert and update but never delete) and records `knowledge` and `marketing` as enabled for every existing project. The old image ignores the table, so rolling back means deploying the previous image; the table stays. `scripts/db-deploy.ts` grants the table and checks that an unscoped read returns nothing.

The weekly autopilot was removed on 2026-10-13: standing assignments are the only planner. With the flag on, the sweep plans assignment runs; with it off, the sweep plans no posts at all, and the web's Marketing page "Assignments" (since 2026-10-19; before, a section of the project settings) lists them once the Orbit Agents route answers and says that Orbit Agents is off when it answers 404. Saved `autopilot_settings` rows stay in the database unused and are still part of the project export; the `configure-autopilot` and `approve-and-schedule` actions and the `…/assignments/autopilot-migration` routes are gone. Missions the autopilot planned earlier keep their slots and are drafted, archived after a missed slot and cleaned up as before; their drafts appear in the general approvals list.

Assignment changes: a change of an active assignment's content returns it to draft, cancels its open runs and withdraws its scheduled posts that are not handed over (`ASSIGNMENT_CHANGED`). An owner's time change keeps the confirmation; posts already scheduled are withdrawn (`ASSIGNMENT_RETIMED`) with one bot notice, and the new times apply from the next run (a day that already has a run is not planned again). A one-off assignment ends by itself (`completedAt`) once its run is done, partial or failed, so it no longer holds its monthly budget share; its scheduled posts still go out, and ending it by hand withdraws them.

Owner release ("Freigeben"): assignment drafts that wait for the owner (the review left them `needs_review`, no bot is linked, or `ORBIT_AGENT_REVIEW_AUTHORITY` is off) are listed on the approvals page under "Anstehende Posts" as "Wartet auf deine Freigabe" (`GET …/assignment-drafts`). Only an owner releases one (`POST …/assignment-drafts/:id/release`): the release records the owner's content review of exactly that text, lets the draft-only mission publish exactly that post (audit `mission.publish_authorized` with `ownerRelease`; preflight binds an assignment mission's publish right to that content, so no other draft of the mission or run gains it), records the package approval in assisted mode and schedules the post through the normal publisher path at its run slot without a veto window (audit `assignment.draft_released`). A taken or passed slot moves to the next free half hour of the same local day under the same slot rules as the veto scheduling; without one the release is refused with `SLOT_UNAVAILABLE` and nothing changes. Every preflight blocker still applies and rolls the whole release back. The assignment must still be confirmed (`confirmedHash`: active, or a one-off that completed its run) and the run not canceled. A second release answers `already_released` with the same publication. A released post is listed under "Anstehende Posts" without a deadline; Stop in Orbit withdraws it until the handoff, and pausing or ending its assignment withdraws it; a content or time change of the assignment does not, because it does not rest on an agent review.

Delivery as Postiz drafts (R73): an assignment with `delivery: "postiz_draft"` (confirmed like every other field; social only; needs `ENABLE_POSTIZ_DRAFTS=true`, else `POSTIZ_DRAFTS_DISABLED` at proposal, change, confirmation and resume) never publishes. Its approved drafts — by an accepted agent review or the owner's release — are booked as `postiz_drafts` handoffs (`queued`, `source: "assignment"`, `slotAt`; audit `assignment.postiz_draft_booked` or `assignment.draft_released` with `postizDraftId`) instead of publications: no veto window, no preview, no publish right. A booked draft holds its run slot (`postizDraftId` on the run slot) under the same slot rules; a taken or passed slot moves to the next free half hour that day, else the deliverable is dropped (`SLOT_UNAVAILABLE`). The worker queue `postiz_draft` sends each once through the shared draft handoff (`postiz-draft.ts`): payload type `draft`, dated at the slot, the run image attached (a failed image is left out and recorded as `imageError`). Before sending it checks again: switch off or slot passed drops the deliverable with a notice; an assignment no longer confirmed for drafts or a canceled run withdraws it; a paused project leaves it queued and the sweep queues it again after the resume (once per project generation). A send interrupted before its outcome was recorded (crash, expired lease, retry) becomes `outcome_unknown` with the exception `POSTIZ_DRAFT_OUTCOME_UNKNOWN` and is never sent again; resolve it with the existing draft resolve action after checking Postiz. A clear rejection fails the handoff, drops the deliverable and gives the slot back. Pause, end, budget exhaustion, content or time change cancel booked drafts that were not sent (owner-released ones only on pause or end); a draft already in Postiz stays and is withdrawn in Postiz. Any publication of such an assignment's content is blocked by preflight (`ASSIGNMENT_DELIVERS_POSTIZ_DRAFTS`); the block reads the delivery stamped on the draft when it was written and the confirmed delivery (recorded with the confirmation), never an unconfirmed change (R74). Confirming another delivery withdraws what the owner released under the old one (`ASSIGNMENT_DELIVERY_CHANGED`, notice `delivery_changed`). While `ENABLE_POSTIZ_DRAFTS` is off, no run is planned for a draft-delivery assignment (no spend) and the bot says so once per day (`drafts_disabled`). The sweep also marks a `sending` handoff without a running job `outcome_unknown` and fails a queued one whose slot passed; an agent-approved draft whose approval no longer counts at send (authority off, bot gone) is canceled with a notice (`AGENT_REVIEW_NOT_ACCEPTED`). The owner's own draft handoff of a content with a queued delivery answers `POSTIZ_DRAFT_QUEUED`. Resolving an unclear draft as not created gives its slot back; resolving it as existing counts it in the daily report. A version the owner already handed over himself counts as delivered and keeps its slot. Notices: `postiz_draft` per created draft ("Entwurf in Postiz angelegt: <Kanal>, <Zeit>" with the text, no Stop), `postiz_error` for an unclear send, `dropped` for a failure or the switch off; the daily report adds "Entwürfe an Postiz". "Anstehende Posts" lists these drafts as "Entwurf in Postiz" without Stop. `run_status` reports them as `postiz_draft_pending`, `postiz_draft` or `postiz_draft_unknown`.

One post per slot across channels (R76): an assignment with `sharedAcrossChannels: true` (social only, confirmed like every other field; absent or `false` keeps one text per channel) writes one text and uses one image per slot for all its channels. The run still holds one slot per channel (`groupAt` on each slot names the requested time it belongs to). The strategy writes one brief per slot group on the group's strictest channel (smallest character limit with the image; with X long posts and an image that is Telegram's 1,024-character caption), one `copywriter` step writes each text once for that channel's rules, and the review judges each text once. When the review settles a text, the same transaction copies it for the group's other channels: one draft-only mission and one content row per channel with byte-identical text, claims, link and image (`sharedFrom` on the copy). Every copy runs the review's deterministic checks on its own channel and slot; a copy that fails them is rejected with the `rejected` notice and its slot is given back, while the other channels go. A clean copy carries the agent review only if its body is byte-identical to the reviewed one; drafts the review leaves for the owner are released per channel. Booking, delivery (Postiz drafts or publications with the veto window), the owner's release and `run_status` then work per channel as before. Previews with Stop (publish delivery) and Postiz draft notices come per channel and post, so a shared slot on two channels sends two previews; Stop on one leaves the other channel's post. If only the text's own (strictest) channel fails its checks (calendar block, quiet hours, a repeat on that channel, its limit, scope), the text still goes to the review and to the other channels, and only that channel's post is rejected with its codes. A revision that fails for the provider leaves the text for the owner on every channel. A text that is dropped (no brief, a copywriter failure, a rejection) is reported for every channel of its slot in the run notice, the rejection notice ("Kanäle: …") and the daily report. A channel without media support gets the text without the image. Duplicate checks look at one channel only, so the same text on X and Telegram is no duplicate, while a repeat of a recent post on one channel still is. The card and the assignments page show "Ein Text und ein Bild für alle Kanäle".

Assignment format (R77): optional confirmed `format` `{minChars, maxChars, hashtags: {min, max}, paragraphs, cta?}` (social only; absent = no format, as before). `cta` must be an https link inside the policy's allowed origins (`LINK_NOT_ALLOWED`) and one of the marketing profile's official links (`FORMAT_CTA_NOT_OFFICIAL_LINK`); the posts then link to it. The strategy and the generation contract receive the format; drafts are written to that length (the appended link not counted), in blank-line paragraphs (plain text, as Postiz receives every post) with the hashtags at the end. The review adds `FORMAT_LENGTH` (body outside `minChars − 10 %` … `maxChars + 5 %`, UTF-16 units as Telegram counts) and `FORMAT_HASHTAGS` (count of `#word` tags with a letter outside `min`…`max`) to its deterministic checks: a draft that only misses the format is revised once without a model call, and a revision that still misses it is rejected. All other checks (claims, links, channel limits, duplicates) are unchanged. A format must fit every channel's limit with its link and the image (`FORMAT_EXCEEDS_CHANNEL_LIMIT` at proposal, change, confirmation and resume). Format problems together with a paused project or another owner-only problem reject the draft (no revision). To remove a format or a banner, ask Orbit to clear it (`assignment_change` with `clear`). Suggested for the uLiquid job: `{minChars: 600, maxChars: 900, hashtags: {min: 2, max: 3}, paragraphs: true, cta: "https://desk.uliquid.vip/en/register"}` with `sharedAcrossChannels: true`; set both with `assignment_change` and confirm the new card. Budget: with one text per slot a run of 2 slots × 2 channels with an image keeps room for one revision per slot at 10 USD/month only narrowly (R76); 20 USD/month leaves ample room.

Assignment banners (R78): optional confirmed `banner` `{template: "brand_landscape", style?}` (social only, needs `image: true` and an approved logo asset as the marketing profile's `visualIdentity.logoAssetId`, else `BANNER_LOGO_REQUIRED` at proposal, change, confirmation, resume and in the visual step before any cost; absent = one free image per run, as before). The visual step generates one 1536×1024 background per run from the default banner style plus `style` (no text, logos or people; `ORBIT_IMAGE_REFERENCES` stays off). The copywriter writes `banner: {headline1, headline2, subline, button}` with every draft (one per slot in shared mode), and Orbit composes one 1600×900 banner per slot over the background with the `brand_landscape` template: approved logo and product name, headline in capitals (white, then cyan), subline, outlined button, divider and the domain of the post's official link. Each banner is an approved asset (`TEMPLATE_GENERATED`, rights from the assignment consent plus the logo) attached to the slot's drafts on every channel and delivered to Postiz like the image before. The review checks the banner copy deterministically (`BANNER_TEXT_OVERFLOW`, `BANNER_UNSUPPORTED_CLAIM` — figures, number words, percentages, status words — and `BANNER_PROHIBITED_LANGUAGE` → one revision naming the words, then reject; `BANNER_TEXT_UNSAFE` — invisible or non-Latin characters —, links and `BANNER_LINK_NOT_OFFICIAL` → reject; `BANNER_IMAGE_MISSING`, `BANNER_RENDER_FAILED`, `BANNER_BRAND_OVERFLOW` → left for the owner; `BANNER_MEDIA_REFUSED` holds back only the channel that cannot carry the image) and shows it to the review model as data (prompt unchanged); the agent review binds the copy (`bannerHash`), and a revision keeps the banner unless its instruction concerns it (`previousBanner`). **R79:** for `delivery: "publish"` the agent's approval of a post with a banner does not stand in for the owner: such posts wait for the owner's release until the review eval set has banner cases and has passed again; with `postiz_draft` the agent's approval creates the Postiz draft as before. A banner stays tied to its sources: it counts and is attached only while it, its background and the logo are approved and hold the same bytes (SHA-256; a Drive sync, a failed sync or a retry changes nothing; other bytes between plan and save give `BRAND_ASSET_CHANGED`, logo bytes that fail their hash `BRAND_ASSET_INTEGRITY_FAILED`); composed banners are bound to their post (`boundTo`) and do not appear in the asset collection, the asset library, pickers or Postiz test images. Without an official link the policy allows, a banner is refused with `BANNER_LINK_NOT_ALLOWED`. The banner logo must be an uploaded `logo` asset (not the bundled EDS mark), and a product name or link domain too wide for the template is refused (`BANNER_BRAND_OVERFLOW`). Text is never cut. Fonts: the runtime image installs Inter (`fonts-inter`, SIL OFL 1.1) next to DejaVu (`fonts-dejavu-core`); the template sets Inter first, with DejaVu Sans, Arial and sans-serif as fallbacks (R80). Upload the logo as a transparent, mark-only PNG; an opaque logo shows its square on the glass card. Set it for the uLiquid job with `assignment_change` (`banner: {template: "brand_landscape"}`) and confirm the new card.

Report assignments: not available yet (R70, I6). Nothing delivers a report run's findings to the bot or the chat, so `contentType: "report"` is refused when an assignment is proposed, changed, confirmed or resumed (`REPORT_NOT_AVAILABLE`, 409), and the Orbit Core tool no longer offers it. The planning code for report runs stays for the follow-up that adds the delivery.

`run_status` derives each run's deliverables from its scheduling, its publications and its Postiz draft handoffs: outcome `scheduled`, `handed_over`, `published`, `stopped`, `withdrawn`, `blocked`, `failed`, `dropped` (with the scheduling code), `awaiting_owner`, or for draft delivery `postiz_draft_pending`, `postiz_draft` and `postiz_draft_unknown`, with publication status, slot, requested slot, veto deadline, `releasedBy` (`agent` or `owner`) and whether Postiz has it; `vetoes` lists the stopped posts with time and source.

Sweep: for every project that is not paused, the worker's sweep creates the runs that are due (one per active assignment and local date, idempotency key `assignment:<id>:<date>`, starting at the preparation lead before the first slot, weekly runs the day before), retries scheduling for runs whose review finished but whose posts were not scheduled, and queues the daily report. `nextSweepAt` wakes the project for the next run start and the next report time.

Queue `agent`: one job is one specialist task (`agent_tasks`) of a run. The task records its own outcome (`done`, `failed`, `canceled`, `outcome_unknown`) and starts the steps that can follow; a task is never repeated after a paid request went out, and a crash after transmission leaves it `outcome_unknown` with its reservation counted. Limits per task: 4 model calls, 6 tool calls, 3 web searches, 120 s and what is left of the run's cost pool (`AGENT_LIMIT`): every paid call of a step must fit the run ceiling (monthly budget / runs per month) less everything the run's tasks hold, and analytics and research also leave 40 % of the ceiling to the required steps (R75). A day whose every slot is unavailable gets no run, only the `slots_unavailable` notice (audit `assignment.day_skipped`). A task of an assignment that is not active, or whose content is not the confirmed one, is refused before any call (`canceled` with `ASSIGNMENT_NOT_ACTIVE` or `ASSIGNMENT_NOT_CONFIRMED`) and the assignment's open runs are canceled. A strategy task first syncs the channel history from Postiz (best effort, outside any transaction, at most once an hour per project; a failure is logged by code and the strategy uses the stored history). Spend is reserved under the run key `assignment-run:<runId>`; reaching the assignment's monthly budget pauses it as `budget_exhausted` (exception `ASSIGNMENT_BUDGET_EXHAUSTED`, Telegram notice). A project budget refusal fails only that task and leaves the assignment active. With the flag off a queued task ends `AGENTS_DISABLED` without a model call. Turns appear under Operations → AI runs as kind `agent`.

Queue `telegram_notification`: previews, notices and the daily report for the owner's bot. Notices: rejected; left for the owner (also a draft the agent approved whose approval does not count while `ORBIT_AGENT_REVIEW_AUTHORITY` is off, one per draft); dropped deliverable at scheduling; slots not free at planning (`slots_unavailable`, one per run); a run that ended with failed or `outcome_unknown` steps, uncovered strategy slots or briefs the copywriter could not write such as `FACT_NOT_USABLE` (`run_problem`, one per run listing every item with its code; budget exhaustion and the project pause are left to their own notices); a post with a veto window or an owner-released post blocked at claim or handoff (`blocked`, one per publication; a Stop or a pause is not reported); budget paused, with the number of scheduled posts it withdrew; posts withdrawn after a time change; Postiz error; project paused (from Orbit, the bot or Slack). The daily report adds the day's failed steps, dropped deliverables and blocked posts (from the audits `assignment.run_problems`, `assignment.run_planned`, `assignment.deliverable_dropped` and `publication.claim_blocked`), and its month cost uses the budget month (UTC month start, like the project and assignment budgets). Report assignments plan no runs until reports have a delivery (R71). `notify()` queues a job inside the transaction of the change it reports (idempotency key `notify:<kind>:<ref>`); nothing is queued without a linked bot or with the flag off. Since WP2.5b the platform owns the queue, `notify` and the delivery (`platform/notifications`), and marketing registers its kinds and renders them; keys and outcomes are unchanged, and with `ORBIT_MODULES` on a notice of a disabled module is skipped as `MODULE_DISABLED`. The sender renders the message when the job runs and reads the state again: a preview of a post that was stopped, handed over or whose deadline has passed is skipped as stale, and a project whose bot is not bound to a current owner gets nothing. Delivery is tried once and retried up to three times after 1, 3 and 9 seconds, only for temporary failures (network errors and timeouts, HTTP 408, 429 and 5xx); after a 429 Telegram's `retry_after` is honoured up to 30 seconds. A refusal that will not change, or an unclear answer after which the message may already be out, is not retried. A photo Telegram refuses falls back to the text alone. A delivery that still fails opens the exception `TELEGRAM_DELIVERY_FAILED` (kind and reference only, never the token or chat id), shown on the approvals page, and is audited. It never changes publishing: the veto deadline applies whether or not the preview arrived. Delivery is at least once; a repeated preview is harmless because Stop is idempotent.

Paused projects: the worker blocks every queued job of a paused project with `PROJECT_PAUSED` except `telegram_notification`, so the pause notice still reaches the owner; previews of posts the pause stopped are skipped as stale. A running specialist makes no further paid call once the project is paused (`PROJECT_PAUSED`, checked in the reservation transaction); a task stopped this way before its first paid call goes back to `queued`, one that had already paid fails. The sweep does nothing for a paused project, so no runs start and no daily report is sent while it is paused. On resume, agent tasks held back by the pause are queued again (the blocked job, or a new job `agent:<taskId>:resume:<generation>`, never twice); a run whose slots all passed during the pause is canceled with `SLOT_UNAVAILABLE` and releases its slots. `/pause` in the bot pauses the project after an inline confirmation (valid 10 minutes); resuming is only possible in Orbit.

Daily report: once per project-local day at 20:00 (`DAILY_REPORT_TIME`, no setting yet), only with a linked bot. It lists posts published that day, posts stopped, drafts created in Postiz ("Entwürfe an Postiz", audit `postiz_draft.accepted`), drafts the review rejected (without those replaced by a revision), the project's settled spend today and this month (all paid calls, not only agents) and any amount with unclear outcome, and up to five facts that expire within seven days.

Telegram webhook: `POST /api/telegram/:projectId/:connectionId`, registered with Telegram as `${APP_ORIGIN}/api/telegram/<projectId>/<connectionId>` when the owner connects the bot (Telegram accepts only HTTPS; otherwise connecting fails with `TELEGRAM_WEBHOOK_URL_INVALID`). It is exempt from the Origin check and authenticated by the per-connection header `X-Telegram-Bot-Api-Secret-Token`, compared in constant time against the stored hash; a wrong or missing secret is answered 401 and audited (`telegram.webhook_rejected`), and an unknown project or connection gets the same 401 (not audited, there is no row to attach it to). Updates from any chat or user other than the bound private chat are ignored and audited. The body limit is 256 KiB and the global rate limit applies. While the flag is off the route answers 404 before any lookup. The bot token is stored encrypted with `CREDENTIAL_KEY` and never returned; the link code (10 minutes, single use) and the webhook secret are stored only as hashes. The bot counts as connected only while the user it is bound to is still a project owner. Connecting again disables the older connection. Buttons are routed by the prefix of their `callback_data` to the handler the platform or a module registered (WP2.5a): `pause:` belongs to the platform, `stop:` to marketing. The data formats are unchanged, so buttons sent by an older version keep working. While `ORBIT_MODULES` is on and a button's module is off, the press is rejected like an invalid one (`telegram.callback_rejected`).

Stop: the bot's Stop button and Stop on the approvals page ("Anstehende Posts", `POST …/publications/:id/veto`) withdraw an assignment post only while Orbit still holds it (`intent_created`, or `blocked_dependency` before any handoff). A post stopped before or already withdrawn by pausing or ending its assignment answers `vetoed`; a post that reached Postiz answers `already_handed_over` and can only be removed in Postiz; an unknown id or a post that is neither an assignment post with a veto window nor one the owner released answers `not_found`. A post is handed over only after its veto deadline (`VETO_WINDOW_OPEN` before it, `VETOED` after a stop). Pausing or ending an assignment withdraws its posts that are not handed over yet.

Failure handling: an exception `PUBLISH_PREFLIGHT_BLOCKED` on an assignment post lists the blockers on the publication; with the flag off, posts that were already scheduled end there because the agent review no longer counts. Unknown outcomes (`outcome_unknown` tasks, publications) are reconciled, never resent. To stop everything at once, pause the project (Orbit or `/pause`).

## Client addresses and rate limits

The API rate limits per client address: 600 reads and 100 writes per minute, 20 per minute on `/api/auth/*`, 10 uploads and 3 image generations per minute. Better Auth adds 3 sign-ins per 10 seconds. The API reaches browsers only through the web proxy, so the proxy forwards the browser's address in `X-Orbit-Client-IP`: the right-most `X-Forwarded-For` entry, which Traefik appends for the connection it accepted (Next.js sets it from the socket when Traefik is absent). Entries further left are client-supplied and ignored. A browser-sent `X-Orbit-Client-IP` is not forwarded.

The API keeps Fastify's `trustProxy` off and believes `X-Orbit-Client-IP` only from a loopback or private-network peer (127/8, 10/8, 172.16/12, 192.168/16, ::1, fc00::/7). From any other peer it uses the peer's own address. It then pins the header to the resolved address for the rest of the request, and Better Auth reads only that header (`apps/api/src/client-ip.ts`, `auth.ts`). Sessions do not store the address.

Trust assumptions: (1) the API publishes no host port, so only Orbit containers on the internal Compose networks can reach it; (2) web is reachable only through Traefik, otherwise a client could choose its own bucket by sending `X-Forwarded-For`. If a CDN or a second proxy (for example a proxied Cloudflare record) sits in front of Traefik, the right-most entry is that proxy's address, and all users behind one edge share a bucket again; Traefik must then trust that proxy's ranges (`forwardedHeaders.trustedIPs`) and the web proxy must skip those hops. IPv6 clients are bucketed per address, not per /64.

## Support (Phase 5)

Support runs only with `ORBIT_SUPPORT=true` **and** the module enabled in the project. The guide is `docs/SUPPORT.md`; app teams use `docs/SUPPORT_WIDGET.md`.

**Mail outage** (the mailbox is down, or IMAP/SMTP fail):
1. **Diagnose.** `GET /api/projects/:id/email` shows `inbound.lastError`. Agent replies end as `not_sent`, `rejected` or `unknown` on the message; the ticket shows it.
2. **Inbound mail.** It waits in the mailbox; Orbit only reads it and fetches it again once the mailbox is back.
3. **Unknown sends.** A reply marked `unknown` is never resent automatically. An agent decides; the owner gets the `EMAIL_OUTCOME_UNKNOWN` exception.
4. **During a long outage.** Answer through the widget, or remove `email` from the inbox's channels.

**Widget abuse** (spam, floods):
1. **Built-in limits.**
   - Platform: 20 new sessions per minute per IP and key; 120 calls per minute per session.
   - Support: 5 conversations per anonymous session; 20 customer messages per conversation in 10 minutes; 10 new e-mail tickets per sender and hour (`support.email.rate_limited` in the audit).
2. **If abuse continues.** Revoke the inbox's widget key (Settings, then Support, then "Widget embed" issues a new one and revokes the old; or the public keys dialog). Then let the app embed the new key, or remove `widget` from the inbox for the time being.
3. **A leaked widget secret.** Use "New widget secret" on the inbox. Old signatures stop working at once. Mario stores the new secret in the app's backend.

**AI kill switch:**
- **One inbox:** set `aiMode` to `off`. No triage or draft job is queued from then on.
- **The whole project:** pause the project. The worker blocks the support AI jobs and no paid call starts.
- **Paid calls are never retried** after a transmit (`SUPPORT_CALL_UNKNOWN`).
- **Spend** shows under category `support_text` and as AI cost per ticket.

**Privacy operations:**
- **Data-subject requests.** In Support, then Contacts, the owner can "Export data" (JSON with tickets, messages, internal notes marked, and attachment references) or "Erase contact". Erasure removes the tickets, messages, attachments with their files, identities, widget sessions, and the mailbox rows of their mails.
- **Retention** runs daily (`support-retention`) with the project's settings. Closed tickets go after 24 months, unsent AI drafts after 90 days, widget sessions 30 days after last seen, contacts once they have no tickets, and the raw files of recorded mails after 90 days. The audit entry `support.retention.applied` holds the counts.
- **Backups** keep erased data until they rotate out; the privacy notice says so.

## Failure and recovery

Pause before intervention. Unknown publication or Slack handoff must remain unknown until observed; do not create a fresh job to resend it. Known publication IDs are read-polled at most eight times with bounded delay. Postiz group cancellation remains a visible manual provider action, because current group scope cannot be proven safely from the list contract.

The Retry UI rechecks job state and maximum attempts; it cannot override budget, policy, source or outcome-unknown gates. Outbox rows survive queue interruption. Expired leases are reclaimed; ambiguous external handoffs are explicitly recorded before recovery. Paid reservations remain in-flight/unknown after a crash; reconcile provider usage rather than resetting them to zero. Never delete the ledger to make a retry pass.

Worker Redis connection failures have exponential backoff capped at 30 seconds and throttled logs. Shutdown allows at most ten seconds before exit. Failed database pumps apply backpressure rather than spawning workers. Parser inputs and deadlines are bounded; PDF extraction runs in a fixed child with a credential-free environment and memory/time limits. There is no shell or infrastructure tool in marketing jobs.

## Data and release maintenance

Source/document revocation purges active chunks/vectors and retained copied payloads while keeping tombstones and minimal audits. Fact withdrawal preserves version history and invalidates its dependents. Metric corrections invalidate insights. Memory retention/deletion is owner-only. Exported project data is private; review it before sharing.

Use `BACKUP_RESTORE.md`. Restore into a new isolated database, pause every project, set Observe and disable external writes before starting services. Keep the credential encryption key in separately controlled encrypted backup; losing it makes stored connector credentials unusable. Off-host transfer, production key escrow and external alarm delivery have not been performed by this task.

Before a release run lint/type checks, all unit/integration tests, the browser suite, production build, generated API contracts, framework validation, dependency audit and secret/license review. CI configuration exists but was not run on a remote repository. Update rates/model capabilities and retest installed provider versions before live activation. Deployment, migration, DNS, account test messages, repository publication and publisher cutover need their own explicit operator authorization.
