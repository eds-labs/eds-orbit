# ADR 0008: Generic action approvals

## Status

Accepted by Mario, 2026-09-30 (alignment plan decision D4, default matrix as written in plan §9.3). Extends [ADR 0002](0002-owner-mandates.md); it does not weaken any existing gate.

## Context

Orbit has five approval flavours with the same core idea but separate storage and code: package-hash approvals for publication (`policy.ts`, `Entity(kind="approvals")`, fixed 24-hour expiry), chat proposal confirmation (`ChatProposal`), signed Slack decisions, the owner live-draft-once action and Postiz draft handoff confirmation. Agents will propose more side effects (Postiz drafts, images, weekly plans), so approvals need one model.

## Decision

1. Actions carry a risk class: `R0` read, `W0` internal write, `C1` paid AI in mandate, `C2` material paid generation, `W1` external non-public write, `W2` external public write, `D1` local deletion, `D2` external deletion, `F1` paid media creation, `F2` budget change, `G` governance.
2. Approval modes: `auto`, `auto_within_policy`, `approval_required`, `approval_required_reauth`, `ui_only`, `forbidden`.
3. Default matrix (plan §9.3): research, planning, analysis and drafts are `auto`; paid model calls are `auto_within_policy`; image generation, Postiz drafts, Drive saves, publishing and schedule changes default to `approval_required` and a project policy may relax them to `auto_within_policy`; local deletion is `approval_required`; external deletion, budget changes and governance changes are `ui_only`; ad campaign creation is `approval_required_reauth`; infrastructure actions are `forbidden`.
4. Hard floors (`D1`, `D2`, `F1`, `F2`, `G`, infrastructure) are code constants. No policy, prompt, imported document or model output can relax them. Agent-initiated actions default one step stricter than user-initiated ones where the mode is configurable.
5. A shared `ActionRequest` record holds action type, risk class, resolved mode with policy version, requester (user, agent run or workflow), package hash, versioned payload reference, optional cost ceiling, per-action-type expiry, decision (user, time, channel, re-authentication) and atomic single-use consumption.
6. Agents never execute side effects. A proposal tool creates the request; the deterministic executor runs after the decision with preflight at claim and immediately before the provider call. Agent runs resume after approval only when they must reason about the approved result.
7. Migration is incremental: existing flows get adapters onto `ActionRequest` one by one; their user-visible behaviour and tests stay unchanged until each adapter is accepted.

## Alternatives

Keeping five flavours avoids a migration but lets approval rules drift. SDK `needsApproval` alone would keep approvals inside run state, which the SDK documentation itself says must be authenticated and consumed server-side.

## Consequences

One approvals inbox and one audit trail for web, Slack and later Telegram decisions. Expiry becomes configurable per action type instead of the fixed 24 hours.

## Addendum 2026-10-02: storage and first consumers

Decided by Mario with the [Orbit Core plan](../plans/ORBIT_CORE_JARVIS_PLAN.md) (D-J2).

- `ActionRequest` is stored as `Entity(kind="action_requests")` without a migration (`apps/api/src/modules/action-requests.ts`). It inherits FORCE RLS, optimistic versions and `EntityVersion` history. It is not a generic collection, so the generic collection routes neither list nor write it.
- Fields: `actionType`, `riskClass`, `approvalMode`, `policy` (id, version), `requestedBy` (user, or agent on behalf of a user), `payload`, `packageHash` (canonical hash of type and payload), `costCeilingMicros`, `status`, `expiresAt`, `decision` (user, decision, time, channel) and `consumedBy` (execution, time).
- Action types are code constants: risk class, approval mode, deciding role and expiry cannot be changed by a policy, prompt, document or model output. The first type is `image.generate`: `C2`, `approval_required`, owner decision, 24 hours. Its payload is bound to the image model and per-image ceiling configured at creation; a different configuration at decision or execution makes it stale.
- A decision must match the version and hash that were shown, comes from an authenticated user and never from the worker's scope, and is idempotent for a repeated identical click. Expired, rejected or already decided requests cannot be approved.
- Approval queues one single-attempt job. The worker runs it with the decider's current project role. The approval is consumed in the same transaction as the budget reservation, after every other precondition, so a failed precondition leaves it unused. A reservation without a result is an unknown outcome and is never sent again.
- Existing approval flavours are unchanged. Content-package start and the decision route follow with the Orbit Core packages (PR2, PR3); publication approvals come later as adapters.
- Second action type (2026-10-02, PR2): `content_package.start`, `C1`, `approval_required`, decided by the requesting editor or owner, 24 hours. Its payload is the deterministic package plan; at decision time the plan is rebuilt from current data and must hash identically (`PACKAGE_STALE` otherwise). Approval creates the package's draft-only missions and generation jobs in the same transaction.
- Owner inbox (2026-10-02): `GET …/action-requests` lists pending, unexpired requests that need an owner, with the exact prompt and ceiling; an editor's package image waits there until an owner decides it.
- Third action type (2026-10-02, Orbit Core J3.1): `content.schedule`, `W2`, `approval_required`, owner only, 24 hours, no cost. Its payload is one package post as proposed: content id and version, text, asset, channel, slot, execution mode and the publishing package hash (`packageFor`, which covers policy, evidence and publisher). At decision time the post and the slot are rechecked (`SCHEDULE_STALE`, `SCHEDULE_SLOT_TAKEN`). Approval lets the draft-only mission publish exactly this post until its slot (audited as `mission.publish_authorized`), records the owner's review of the shown text, records the assisted-mode approval until the slot, and calls `publishIntent`; the request is consumed in the same transaction, and any preflight blocker rolls the whole decision back. The existing publisher still runs its full preflight immediately before the handoff. Since J3.4 the slot is written to the draft only on approval, and a request with `replacesPublicationId` moves a scheduled post: approval cancels the old publication and schedules the new slot in the same transaction.

## Addendum 2026-10-09: assignment confirmation and agent review authority

Decided by Mario with the [Orbit Agents design](../superpowers/specs/2026-10-09-orbit-agents-design.md) (D2, D3, D4), behind `ORBIT_AGENTS`. No hard floor of decision 4 changes: deterministic blockers stay absolute, and nothing here relaxes a check for content without an assignment.

### Fourth action type: `assignment.confirm`

`W0`, `approval_required`, owner only, 7 days, no cost. Orbit Core (`assignment_propose`), an editor, or the autopilot migration card proposes an assignment; it is stored as a draft and its payload is the whole assignment content plus `assignmentHash` (the hash of every content field: name, kind, schedule, content type, channels, topic frame, tone, image, style references, veto window, monthly budget; never status or confirmation). At decision time the draft must still have that hash, the policy must still allow its channels and content type, and the confirmed assignments plus this one must fit the project's monthly budget (`ACTION_REQUEST_STALE`, `SCOPE_NOT_ALLOWED`, `ASSIGNMENT_BUDGET_EXCEEDS_PROJECT`). Approval activates exactly the shown content and records the confirmation (user, time, `assignmentHash`, image-rights consent); an assignment with images is refused without the consent (`IMAGE_RIGHTS_CONSENT_REQUIRED`). A content change returns the assignment to draft with a new request and cancels the old one; it also cancels the assignment's open runs and withdraws its scheduled posts that are not handed over (`ASSIGNMENT_CHANGED`), and the specialist runner refuses tasks of an assignment that is not active or whose content is not the confirmed one (`ASSIGNMENT_NOT_ACTIVE`, `ASSIGNMENT_NOT_CONFIRMED`, task `canceled`, no cost). Moving the times (owner only) keeps the confirmation and moves its hash with them; the posts already scheduled were reviewed under the old hash, so they are withdrawn (`ASSIGNMENT_RETIMED`) with one Telegram notice, and the new times apply from the next run. Pausing (editors too) and resuming (owner only) do not need a new confirmation. A one-off assignment ends by itself once its run is over (`completedAt`); its confirmation still covers that run's posts, and ending it by hand afterwards withdraws those not handed over. The confirmation is the owner's publishing approval for the posts the assignment produces, with the veto window as the safety net (spec D3).

### Agent review authority (spec §6)

Free marketing text normally needs the owner's review of the exact text (`humanReviewedBodyHash`). The review specialist's `approve` records `agentReview` (body hash, review task, assignment id, version and hash, deterministic check result, `checkedAt`; `reviewedBy` is `agent:<taskId>`, never a person). `agentReviewAccepted` (`apps/api/src/modules/agents/agent-review.ts`) lets it stand in for the owner review only when all of these hold:

1. `ORBIT_AGENTS` is on, and `ORBIT_AGENT_REVIEW_AUTHORITY` is on. The second switch (default `false`) is the explicit gate of spec §6: it is set only after the live review eval has passed (rollout Approval J). While it is off, no agent review stands in for the owner, even with a linked bot: previews and Stop still work, and assignment posts wait for the owner.
2. The assignment is `active` (or a one-off that ended by completing its run) and its confirmation hash equals the hash of its current content, and the review was made under that same confirmation hash. A content or time change therefore voids earlier reviews; a pause and resume does not.
3. The content's type and channel are inside the confirmation (`contentType` and `channels` of the assignment).
4. The review is from the review task of the content's own run, covers exactly the current body (`bodyHash`), and recorded no deterministic problem; the text names no link outside the policy.
5. A Telegram bot is linked by a user who is still a project owner, and the review was made after the link (`checkedAt >= linkedAt`). A review made without a linked bot never gains authority later; without one, assignment posts wait for the owner as before. The owner releases such a draft with "Freigeben" (`POST …/assignment-drafts/:id/release`, owner only, R70): the owner's review of the exact text, a publish right of the draft-only mission bound to that one content, and a publication without a veto window at the run slot; every preflight blocker still applies.
6. The publication carries a veto deadline that has passed without a stop. The deadline belongs to the publication: `claimPublication` holds a post whose window is still open (`VETO_WINDOW_OPEN`) or that was stopped (`VETOED`), and refuses agent-reviewed content that would go out without any window (`VETO_DEADLINE_REQUIRED`). Preflight runs again immediately before the handoff.

Deterministic problems are checked before the model sees a draft; any of them rejects it without a model approval path, and `revise` allows one rewrite and one second review. Project-level problems that are no fault of the draft (`PROJECT_PAUSED`, `POLICY_EXPIRED`, `POLICY_REQUIRED`) and an unverifiable bare host (`LINK_UNVERIFIED`) leave the draft for the owner (`needs_review`, problems recorded, no agent approval), as do revision failures of the provider (`MODEL_OUTCOME_OR_COST_UNKNOWN`, `MODEL_REQUEST_NOT_ACCEPTED`). An outage or ambiguity is not a review verdict.

Only for a publication created by `scheduleApproved` (it carries `vetoDeadline` and `assignmentRunId`) the accepted review, the veto deadline and the missing stop also satisfy `APPROVAL_REQUIRED` (assisted mode, instead of a package approval per post) and `MISSION_TEST_WRITE_NOT_AUTHORIZED` / `MISSION_LIVE_WRITE_NOT_AUTHORIZED` (assignment missions stay draft-only; the confirmed assignment authorizes the post). At intent (when `scheduleApproved` creates the publication) the window must be valid; at handoff it must have passed. A publication without a veto deadline keeps every one of these codes. Each automatic approval is audited with the assignment version, the review task, the check result and the veto deadline.

### Stop

A stop (Telegram button or `POST …/publications/:id/veto`, editors and owners) withdraws a publication only from an allow-list: `intent_created`, or `blocked_dependency` before any handoff (no `handoffAt`, no remote ID). Its answers: `not_found` for an unknown id or a publication without a veto window; `vetoed` for a post it withdraws, one stopped before, or one already withdrawn by pausing or ending its assignment (it will not go out either, R57); `already_handed_over` for everything that has reached Postiz, which changes nothing — such a post can only be removed in Postiz. The stop is bound to the publication version that was shown, is idempotent, and its callback token in Telegram is an HMAC of the publication id and version, resolved only within the bot's own project. Automatic approvals are audited as `content.agent_approved` and `publication.agent_scheduled`. Pausing or ending an assignment withdraws its posts that are still withdrawable in the same way. A Telegram delivery failure never extends a publishing right: the deadline applies whether or not the preview arrived.
