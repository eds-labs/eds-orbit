# Platform files

Modules store binary files through the platform's file service (WP4.6): support attachments and raw e-mail. Content is encrypted before it is stored; Orbit's `File` table holds the metadata under row-level security. Marketing's brand assets are unchanged and stay in `Entity` data.

Files are off unless `ORBIT_FILES=true` and an encryption key is present. Otherwise every file route answers 404 and the service refuses with `FILES_NOT_CONFIGURED`.

## Where the content lives

`FILES_BACKEND` chooses (Mario, 2026-10-17: database for the pilot):

| Backend | Content in | Backup | Needs |
|---|---|---|---|
| `database` (default) | encrypted rows in `FileBlob` (Postgres, project RLS, deleted with the project) | part of the database backup | the encryption key only |
| `s3` | an own S3-compatible bucket (Cloudflare R2), never the backup bucket | the bucket's own durability | bucket, bucket-scoped token, key |

The encryption key `FILES_ENCRYPTION_KEY` is generated by Coolify (`SERVICE_HEX_64_FILESKEY`), like `CREDENTIAL_KEY`. Without it, stored files cannot be read, and that includes restored backups. Keep a copy of it next to the other Orbit secrets.

Moving to `s3` later needs only the bucket settings; existing rows would have to be copied over (a follow-up script). The modules notice nothing.

## Setting up a bucket (only for FILES_BACKEND=s3)

1. **Bucket.** Cloudflare → R2 → Create bucket, for example `orbit-files`, no public access.
2. **Token.** R2 → Manage API tokens → *Object Read & Write*, this bucket only.
3. **Coolify.** Set:
   - `FILES_BACKEND=s3`;
   - `FILES_S3_ENDPOINT` (`https://<account-id>.r2.cloudflarestorage.com`);
   - `FILES_S3_BUCKET`;
   - `FILES_S3_ACCESS_KEY_ID` and `FILES_S3_SECRET_ACCESS_KEY`.

The backup container never receives `FILES_*`, and api/worker never receive `BACKUP_*`; the compose check enforces both.

## How it works

- **Encryption.** Each file is encrypted with AES-256-GCM before upload, using a fresh IV and the file id as additional data. A download checks the tag and the SHA-256 before anything is sent. R2's own at-rest encryption comes on top.
- **Object keys.** `projects/<projectId>/<moduleId>/<fileId>`: no name, no content, no user. The database backend also refuses a key of another project, both in code and by a check constraint.
- **Routes:**

  | Route                                      | Needs                                                                                                                           |
  | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
  | `POST /api/projects/:id/files?module=<id>` | write access in the module; the body is the raw bytes (`application/octet-stream`) with headers `x-file-type` and `x-file-name` |
  | `GET /api/projects/:id/files/:fileId`      | read access in the file's module; sent as an attachment with `nosniff` and a sandboxing CSP                                     |
  | `DELETE /api/projects/:id/files/:fileId`   | write access in the file's module                                                                                               |

  A switched-off module's files answer 404 `MODULE_DISABLED`.

- **Limits.**
  - Size: `FILES_MAX_BYTES`, default 20 MB, at most 50 MB.
  - Types:
    - images (PNG, JPEG, GIF, WebP) and PDF, each checked by its file signature;
    - plain text, CSV and `message/rfc822`.
- **Deleting.** A deleted file is unreadable at once. The object and the row follow right away. If the bucket fails, the hourly `file-cleanup` task retries.

## Limits and follow-ups

- Deleting a whole project removes its rows, and with the database backend its content too (cascade). With `s3` the objects stay; a purge of the project's key prefix is a follow-up.
- There is no virus scanning. Downloads are always attachments, never rendered inline.
- Key rotation for `FILES_ENCRYPTION_KEY` is not supported yet; changing it makes existing files unreadable.
